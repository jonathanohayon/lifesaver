LIFE.SAVER v0.6.0
Phase 2.5 — Action Events Table Migration

================================================================================
PURPOSE
================================================================================

This phase creates the action_events table.

The table is the audit trail for V2 action lifecycle changes. It records what happened to an action, when it happened, which workspace it belongs to, and which user/system component caused the change when known.

This phase is intentionally storage-only.
It does not add approval APIs, executors, social publishing, support sending, ad controls, auto-run policies, or external write connectors.

================================================================================
WHY THIS TABLE IS NEEDED
================================================================================

V2 changes LIFE.SAVER from Advisor Mode toward Operator Mode.
Before LIFE.SAVER can execute anything, every proposed/approved/rejected/executed/failed/rolled-back action must be auditable.

The actions table stores the current state.
The action_events table stores the history of how the action reached that state.

This is important for:
- founder trust
- debugging
- client handoff
- compliance-style review
- rollback analysis
- future approval queue timeline UI
- future policy explanation UI
- future executor result review

================================================================================
MIGRATION FILE
================================================================================

Added file:

database/migrations/010_create_action_events_table.sql

Migration style:
- Non-destructive
- Additive only
- Uses CREATE TABLE IF NOT EXISTS
- Uses CREATE INDEX IF NOT EXISTS
- Does not alter or drop V1 tables
- Does not rename existing columns
- Does not execute external actions

================================================================================
TABLE: action_events
================================================================================

Fields:

id
- UUID primary key
- generated by gen_random_uuid()
action_id
- UUID
- required
- references actions(id)
- cascade delete if action is deleted

workspace_id
- UUID
- required
- references workspaces(id)
- used for workspace-safe audit queries
- service logic must keep this aligned with actions.workspace_id

actor_user_id
- UUID
- optional
- references users(id)
- set null if user is deleted
- null allowed for system/worker/future policy events

event_type
- text
- required
- constrained to approved event values

from_status
- text
- optional
- previous action status
- constrained to approved lifecycle statuses when present

to_status
- text
- optional
- new action status
- constrained to approved lifecycle statuses when present

message
- text
- optional
- human-readable safe summary
- must not be blank when provided

metadata_json
- JSONB
- required default {}
- safe structured metadata
- never store secrets here

created_at
- timestamptz
- required default now()

================================================================================
EXAMPLE EVENT FLOWS
================================================================================

Manual approval flow:

1. action_created
   from_status: null
   to_status: proposed

2. policy_evaluated
   from_status: proposed
   to_status: approval_required

3. approved
   from_status: approval_required
   to_status: approved

4. queued
   from_status: approved
   to_status: queued

5. execution_started
   from_status: queued
   to_status: executing

6. execution_finished
   from_status: executing
   to_status: executed

Rejected flow:

1. action_created
2. policy_evaluated
3. rejected

Failed execution flow:

1. action_created
2. approved
3. queued
4. execution_started
5. execution_failed

Rollback flow:

1. rollback_requested
2. rollback_started
3. rollback_finished

================================================================================
SECURITY RULES
================================================================================

action_events.metadata_json must never contain:

- API keys
- OAuth access tokens
- refresh tokens
- passwords
- raw .env values
- DATABASE_URL
- Claude API key
- Triple Whale API key
- APP_ENCRYPTION_KEY
- WORKER_SHARED_SECRET
- raw customer payment/card data
- unnecessary full support ticket bodies

Admin UI should show safe summaries, not raw sensitive payloads.

================================================================================
SERVICE LOGIC NOTES FOR FUTURE PHASES
================================================================================

The database cannot fully guarantee that action_events.workspace_id equals actions.workspace_id because that requires cross-table validation logic.

Future repository/service functions must enforce:

- load the action first
- use action.workspace_id when inserting action_events
- never accept workspace_id blindly from the browser
- scope all reads by workspace_id
- normal customers cannot see other workspace events
- Super Admin can monitor without seeing secrets

================================================================================
WHAT THIS PHASE DOES NOT DO
================================================================================

This phase does not:

- create approval queue APIs
- create action detail APIs
- approve actions
- reject actions
- cancel actions
- execute actions
- publish social posts
- send support replies
- pause campaigns
- adjust ad budgets
- write to Triple Whale
- write to Shopify, Meta, Google, TikTok, Snapchat, Gmail, or any external platform
